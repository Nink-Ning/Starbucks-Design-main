# Starbucks Design 设计决策规范

## 1. 文档目的

本文用于指导 Codex、Claude Code、Cursor 等工程代理，在 Starbucks Design / DesignKit 项目中处理企业级中后台界面时，做出一致、可解释、可复用的设计决策。

本文重点解决以下问题：

- 页面应该采用左右结构还是上下结构；
- 操作应放在页面头部、工具栏、行内还是底部；
- Modal、Drawer、侧栏、新页面应该如何选择；
- 筛选区、表格工具栏、批量操作、列设置和分页应该如何组织；
- 表单、详情、Dashboard 应如何分组和建立信息层级；
- Loading、Empty、Error、Permission 等状态应该如何设计；
- 响应式、窄屏和横向溢出应该如何处理；
- AI 在信息不完整时应如何判断、报告和降级。

本文不替代：

- `AGENTS.md`；
- `skills/starbucks-design/SKILL.md`；
- `references/architecture.md`；
- `references/task-routing.md`；
- `agent-guidelines/` 中的专项规范；
- React / Vue 组件 Skill 的 API 文档；
- 已评审通过的 Figma 设计稿与 Variables。

---

## 2. 设计决策总原则

所有设计决策应优先满足以下目标：

```text
帮助用户完成任务
→ 保持信息结构清晰
→ 缩短操作路径
→ 降低理解和操作成本
→ 保持跨页面一致
→ 复用已有组件和模式
→ 保证 React / Vue 可实现
→ 保证状态、异常和响应式完整
```

不得仅根据个人偏好、单张截图或流行样式做决定。

每个关键设计决策至少应基于以下维度：

1. 用户目标；
2. 核心任务；
3. 操作频率；
4. 内容体量；
5. 信息层级；
6. 与当前主体的关联性；
7. 风险等级；
8. 是否需要对照上下文；
9. 是否需要独立 URL；
10. 是否需要保存、恢复或继续处理；
11. 是否存在既有统一模式；
12. 是否能由现有组件支持。

---

## 3. 决策输出格式

涉及布局、容器、操作、筛选或信息结构的任务，建议按以下格式输出：

```text
任务目标：
主要用户：
核心动作：
内容体量：
操作频率：
风险等级：
上下文关联：
推荐方案：
不推荐方案：
选择依据：
适用边界：
异常状态：
响应式策略：
需要复用的组件：
待确认项：
```

不得只给出“建议用 Drawer”或“建议放右侧”而没有解释依据。

# 第一部分：布局决策

## 4. 页面整体布局选择

### 4.1 上下结构

适用：

- 用户需要按从上到下的顺序完成任务；
- 页面以浏览、筛选、查看结果为主；
- 页面内容具有明显先后关系；
- 主内容宽度要求较高；
- 不需要长期保留左侧上下文；
- 适合列表、详情、表单、Dashboard。

典型结构：

```text
PageHeader
↓
说明 / 筛选 / 概览
↓
核心内容
↓
补充信息
```

常见场景：

- 筛选列表页；
- 基础详情页；
- 表单页；
- Dashboard；
- 结果页。

### 4.2 左右结构

适用：

- 左侧用于稳定导航、分类或对象选择；
- 右侧用于查看和操作当前对象；
- 用户需要频繁切换左侧对象；
- 左右区域有明确主从关系；
- 左侧内容宽度相对稳定；
- 右侧需要保留较大操作空间。

典型结构：

```text
左侧：分类 / 树 / 标签组
右侧：筛选 / 工具栏 / 主内容
```

常见场景：

- 标签管理；
- 组织树 + 用户表格；
- 分类 + 商品列表；
- 左树右表；
- 配置中心。

不适用：

- 左侧内容只是临时筛选项；
- 左侧内容很少且无需持续可见；
- 右侧主内容在常见屏幕下明显过窄；
- 移动端无法自然折叠。

### 4.3 单列布局

适用：

- 内容线性；
- 字段较少；
- 用户需要聚焦；
- 信息关系简单；
- 表单或详情强调可读性。

推荐用于：

- 基础表单；
- 登录；
- 结果页；
- 简单详情。

### 4.4 多列布局

适用：

- 字段较多；
- 字段之间存在横向关联；
- 页面宽度足够；
- 需要提升信息密度；
- 字段长度较短且可预测。

约束：

- 不得为了压缩高度盲目多列；
- 长文本、说明、上传、富文本默认跨整行；
- 错误提示不得被列宽挤压；
- 窄屏下应自然降为更少列；
- React / Vue 响应式结果应一致。

---

## 5. 主次区域关系

### 5.1 主内容优先

页面中只能有一个主要视觉和任务中心。

主内容通常是：

- 当前表格；
- 当前表单；
- 当前详情；
- 当前图表分析；
- 当前任务处理区。

辅助内容包括：

- 说明；
- 状态；
- 快捷入口；
- 次要统计；
- 操作历史；
- 帮助信息。

辅助内容不得与主内容争夺视觉层级。

### 5.2 信息层级建议

```text
一级：页面目标与核心任务
二级：当前对象或关键状态
三级：主要数据与操作
四级：辅助说明与历史信息
```

避免：

- 每个模块都使用同等级标题；
- 所有区域都使用卡片；
- 所有操作都使用主按钮；
- 通过大量边框制造层级。

---

## 6. 页面容器与间距

优先使用项目已定义的页面 Token 和模板间距。

建议保持以下关系：

```text
页面外边距
> 区块间距
> 标题与内容间距
> 控件内部间距
```

不得：

- 每个页面自行定义一套边距；
- 使用大量随机数值；
- React 与 Vue 分别维护不同间距；
- 通过空白 div 控制间距；
- 用组件内部 margin 修复页面布局。

页面模板应通过：

- 页面容器；
- 区块容器；
- Stack / Space / Grid；
- 共享 CSS 变量；

统一控制布局节奏。

# 第二部分：容器选择

## 7. Modal、Drawer、侧栏和新页面选择

容器选择必须综合：

- 内容体量；
- 任务复杂度；
- 与当前页面主体的关联性；
- 用户是否需要对照当前页面；
- 是否需要独立 URL；
- 是否需要保存草稿；
- 是否可能中断后继续；
- 是否包含多步骤；
- 是否存在高风险操作；
- 是否需要大面积预览。

---

## 8. Modal

### 8.1 适用

- 内容少；
- 操作短；
- 上下文关联强；
- 用户无需离开当前页面；
- 一次完成；
- 不需要独立 URL；
- 不需要复杂导航；
- 不需要大面积预览。

典型场景：

- 删除确认；
- 简单新增或编辑；
- 少量字段确认；
- 风险提示；
- 影响范围摘要；
- 单次选择。

### 8.2 不适用

- 表单字段很多；
- 需要多步骤；
- 需要查看大量上下文；
- 内容可能出现长列表；
- 需要保存草稿；
- 操作时间长；
- 需要返回继续；
- 需要独立链接；
- 内部还要嵌套复杂弹层。

### 8.3 Modal 规则

- 标题明确表达任务；
- 主操作和取消操作稳定；
- 危险操作使用危险语义；
- 内容区可滚动，标题和底部操作稳定；
- 不得通过无限加宽解决内容过多；
- 不得在 Modal 中再嵌套同层级 Modal；
- 关闭前存在未保存内容时需确认；
- Enter、Esc、关闭按钮行为要一致。

---

## 9. Drawer

### 9.1 适用

- 与当前对象关联强；
- 用户需要边看列表边编辑；
- 内容中等；
- 需要比 Modal 更大空间；
- 仍希望保留当前页面上下文；
- 适合创建、编辑、查看详情。

典型场景：

- 表格行编辑；
- 对象详情；
- 创建编辑表单；
- 批量操作配置；
- 列设置；
- 筛选高级配置。

### 9.2 不适用

- 多步骤长流程；
- 大量复杂内容；
- 需要独立 URL；
- 需要跨页面分享；
- 需要全屏比较；
- 页面本身已经有右侧固定面板；
- 移动端体验会明显受限。

### 9.3 Drawer 规则

- 宽度根据内容而不是固定习惯决定；
- 表单项较多时使用分组；
- 操作区保持稳定；
- 长内容允许内部滚动；
- 关闭后需要恢复原页面状态；
- 与当前选中行或对象关联明确；
- 避免层层嵌套 Drawer；
- Popup 必须在 Drawer 中可见和可操作。

---

## 10. 固定侧栏

### 10.1 适用

- 辅助信息需要长期可见；
- 用户需要持续对照；
- 侧栏本身不是临时任务；
- 适合筛选、目录、上下文、属性面板；
- 主区域和侧栏可同时操作。

典型场景：

- 左侧树；
- 标签分组；
- 属性面板；
- 页面内目录；
- 配置中心导航。

### 10.2 规则

- 明确主次关系；
- 侧栏宽度稳定；
- 支持折叠时保留可识别入口；
- 不得挤压主内容到不可用；
- 窄屏时应切换为 Drawer、顶部选择或独立入口；
- 侧栏滚动和页面滚动职责清楚。

---

## 11. 新页面

### 11.1 适用

- 内容多；
- 流程复杂；
- 多步骤；
- 需要独立 URL；
- 需要分享、刷新、返回；
- 需要保存草稿；
- 用户可能中断后继续；
- 需要大量上下文；
- 需要宽屏内容；
- 需要权限、状态和历史记录。

典型场景：

- 复杂创建编辑；
- 分步配置；
- 详情工作台；
- 审批任务；
- 大型数据分析；
- 独立配置流程。

### 11.2 规则

- 返回路径明确；
- 页面状态可恢复；
- 草稿和正式生效状态清晰；
- 页面头部体现对象和状态；
- 长流程提供进度；
- 关键操作位置稳定；
- 需要时支持 URL 参数或路由状态。

---

## 12. 容器选择速查

| 条件 | 推荐容器 |
| --- | --- |
| 关联强、内容少、一次完成 | Modal |
| 关联强、内容中等、需保留上下文 | Drawer |
| 辅助内容长期可见 | 固定侧栏 |
| 内容多、流程复杂、需独立 URL | 新页面 |
| 高风险确认、信息少 | Modal / Popconfirm |
| 行编辑、对象详情 | Drawer |
| 多步骤配置 | 新页面 |
| 列设置、筛选配置 | Drawer / Popover，按复杂度判断 |
| 简单确认 | Popconfirm / Modal |

# 第三部分：操作决策

## 13. 主操作与次操作

### 13.1 主操作

页面或容器中通常只应有一个最主要操作。

主操作应满足：

- 与当前核心任务直接相关；
- 用户完成任务的主要下一步；
- 视觉优先级最高；
- 文案明确；
- 状态完整；
- 不与危险操作混淆。

示例：

```text
创建
保存
提交
发布
查询
确认
```

### 13.2 次操作

次操作包括：

```text
取消
返回
重置
保存草稿
导出
预览
更多
```

次操作不得与主操作使用相同视觉权重。

### 13.3 危险操作

危险操作包括：

```text
删除
停用
解绑
覆盖
清空
撤销发布
```

规则：

- 使用危险语义；
- 说明影响；
- 需要时二次确认；
- 不与主操作并排造成误触；
- 批量危险操作必须明确数量和范围；
- 不得只通过颜色表达风险；
- 异步执行期间禁止重复提交。

---

## 14. 页面头部操作

适合放置：

- 页面级创建；
- 页面级发布；
- 全局导入；
- 全局设置；
- 与整个页面对象相关的操作。

不适合放置：

- 行操作；
- 表格筛选；
- 批量操作；
- 仅对局部模块生效的操作。

页面头部操作在窄屏下应：

- 支持换行；
- 次要操作进入“更多”；
- 保留主操作；
- 不遮挡页面标题和状态。

---

## 15. TableToolbar 操作布局

建议结构：

```text
Start：
已选摘要
批量操作
更多操作
核心 Quick Filter（可选）

Controls：
常规 Quick Filter
刷新
列设置入口
导出入口
```

新增、导入等创建数据的操作属于 Page Header 或对应业务流程，不属于 TableToolbar。密度管理不是当前 TableToolbar 的统一职责；只有未来公共 API 和对应 Profile Knowledge 明确登记后才可使用，不得从旧示例或页面私有配置推断。

具体顺序应结合业务目标，但需保持：

- 核心操作靠近数据；
- 批量操作靠近选择反馈；
- 工具类操作集中；
- 不把所有按钮平均分布；
- 窄屏下支持折叠或换行。

---

## 16. 批量操作

### 16.1 触发

批量操作仅在存在选中项时出现或激活。

### 16.2 位置

推荐：

- 表格左上方；
- 与“已选择 N 项”相邻；
- 或使用固定批量操作条。

不推荐：

- 放在表格右上角远离复选框；
- 与列设置、导出混在一起；
- 放在分页之后；
- 选中前就显示大量不可用按钮。

### 16.3 反馈

必须说明：

- 已选择数量；
- 操作范围；
- 是否跨页；
- 是否影响不可见数据；
- 成功数量；
- 失败数量；
- 部分失败原因；
- 是否可重试。

### 16.4 危险批量操作

必须明确：

```text
将影响 N 条数据
是否包含跨页数据
是否可恢复
是否需要输入确认
```

---

## 17. 行操作

### 17.1 适用

- 只作用于单条记录；
- 与当前行关系直接；
- 高频操作数量少。

### 17.2 规则

- 高频操作直接展示；
- 低频操作进入“更多”；
- 危险操作与普通操作区分；
- 保证点击目标清晰；
- 操作列宽度稳定；
- 固定列时阴影和层级正确；
- 不把所有操作都做成主按钮。

---

## 18. 操作反馈

每个重要操作必须考虑：

```text
执行前
→ 是否需要确认

执行中
→ Loading、禁用、进度

执行成功
→ 成功反馈、数据更新

执行失败
→ 原因、重试、保留输入

部分成功
→ 成功/失败明细

中断或关闭
→ 是否保存、是否恢复
```

仅显示“操作失败”通常不足以支持用户恢复。

# 第四部分：筛选与数据决策

## 19. 筛选层级

筛选一般分为：

```text
快速搜索
常用筛选
高级筛选
已生效筛选
保存筛选
```

不得把所有字段同时展示。

---

## 20. 快速搜索

适用：

- 用户主要通过关键词找对象；
- 搜索字段明确；
- 操作频率高；
- 输入后能快速得到结果。

规则：

- Placeholder 说明搜索对象；
- 支持清空；
- 明确触发方式；
- 避免和 FilterBar 中同一字段重复；
- 搜索建议和历史仅在有价值时加入。

---

## 21. FilterBar

### 21.1 常用字段优先

常用字段应：

- 默认展示；
- 顺序稳定；
- 与用户任务相关；
- 不因技术字段顺序排列。

### 21.2 展开收起

适用：

- 字段较多；
- 大部分用户只使用少数字段；
- 需要保持页面紧凑。

规则：

- 展开后不改变已输入值；
- 收起后隐藏字段仍保留还是清除必须有明确契约；
- 显示隐藏条件数量时文案清晰；
- 响应式列数使用真实组件能力；
- 查询和重置位置稳定。

### 21.3 查询模式

常见模式：

```text
Manual
用户点击查询后生效

Change
字段变化后自动生效
```

选择依据：

- 查询成本；
- 数据量；
- 是否会频繁请求；
- 用户是否需要组合多个条件；
- 是否存在复杂校验。

高成本查询、复杂组合筛选优先 Manual。

低成本、即时反馈场景可使用 Change。

### 21.4 重置

重置必须明确：

- 重置到空值；
- 重置到默认值；
- 是否立即重新查询；
- 是否清除高级筛选；
- 是否清除隐藏字段；
- 是否清除已保存筛选。

---

## 22. 高级筛选

适用：

- 条件复杂；
- 支持逻辑关系；
- 字段很多；
- 低频使用；
- 需要保存或复用。

容器选择：

- 内容较少：Popover；
- 中等复杂：Drawer；
- 很复杂或需要独立管理：新页面。

高级筛选结果应通过：

- 条件摘要；
- 标签；
- 已生效条件区域；

反馈给用户。

---

## 23. TableToolbar

TableToolbar 应统一处理：

- 已选摘要；
- 批量操作的展示顺序、禁用、Loading 和响应式折叠；
- 1～3 个轻量 Quick Filters 的容器和提交时机；
- 操作状态展示；
- 刷新、列设置、导出等已发布 Table Tools 的入口和语义事件；
- 更多操作的合并与优先级。

它不应承担：

- 新增、导入等创建数据的页面级入口；
- 密度管理；
- FilterBar 的字段管理；
- Table 的分页内部逻辑；
- 页面路由；
- 特定业务接口；
- 行操作逻辑；
- 危险操作确认、导出文件生成或列设置面板实现。

Starter Profile 只使用当前页面模板批准的 TableToolbar 子集。Docs Full Profile 可以进行 React/Vue framework usage、公开 API integration 和公开扩展边界内的 advanced customization；两个 Profile 的 Capability ID 和边界读取 `profile-routing.md` 与 `capability-registry.md`。

---

## 24. 列设置

### 24.1 适用

- 列较多；
- 用户角色差异明显；
- 默认列无法满足全部用户；
- 表格横向滚动严重。

### 24.2 能力

可包括：

- 显示 / 隐藏；
- 排序；
- 固定；
- 恢复默认；
- 保存个人偏好。

### 24.3 规则

- 关键主列默认不可隐藏或需谨慎；
- 操作列通常保持可用；
- 恢复默认入口明确；
- 列设置变化实时还是确认后生效必须一致；
- React / Vue 表现等价。

---

## 25. 导出

导出前必须判断：

- 导出当前页还是全部；
- 是否按当前筛选；
- 是否包含隐藏列；
- 数据量是否大；
- 是否异步；
- 是否需要导出记录；
- 是否包含敏感数据；
- 是否需要权限。

小数据可即时下载。

大数据应使用异步导出任务，并提供：

- 任务状态；
- 完成通知；
- 下载入口；
- 失败原因；
- 过期说明。

---

## 26. 分页

分页应明确：

- 当前页；
- 每页数量；
- 总数；
- 是否支持跳页；
- 是否支持调整页大小；
- 筛选后是否回到第一页；
- 删除当前页最后一条后的行为；
- 是否支持跨页选择。

分页通常位于表格底部。

不得把分页作为 TableToolbar 的普通按钮。

---

## 27. 跨页选择

跨页选择必须明确：

```text
仅选当前页
选中当前筛选结果
选中全部数据
```

用户必须知道：

- 当前选择范围；
- 是否包含不可见数据；
- 更改筛选后如何处理；
- 批量操作影响多少条；
- 是否可以清除全部选择。

---

# 第五部分：表单决策

## 28. 基础表单

适用：

- 字段较少；
- 流程简单；
- 一次完成；
- 字段关系清晰。

推荐：

- 单列优先；
- 相关字段可双列；
- 操作区稳定；
- 错误就近展示；
- 必填项清晰；
- 帮助信息贴近字段。

---

## 29. 分组表单

适用：

- 字段较多；
- 存在明显主题；
- 用户需要分块理解；
- 信息可分为基础、规则、范围、通知等。

分组方式：

- 标题；
- 说明；
- 分割；
- Card；
- 折叠面板。

避免所有分组都使用重卡片，造成页面过重。

---

## 30. 分步表单

适用：

- 流程有明确先后；
- 后续步骤依赖前一步；
- 单页过长；
- 需要分阶段校验；
- 用户需要了解进度。

规则：

- 步骤名称表达任务；
- 当前、已完成、错误状态明确；
- 返回上一步不丢失数据；
- 最后一步明确确认范围；
- 长流程支持草稿；
- 终态提供结果和下一步；
- 不得只为了视觉而拆步骤。

步骤较少且横向空间足够可使用横向 Steps。

步骤较多或说明较多可使用纵向 Steps。

---

## 31. 表单操作区

常见顺序：

```text
主操作：保存 / 提交 / 下一步
次操作：取消 / 返回 / 上一步
辅助操作：保存草稿 / 预览
```

规则：

- 操作位置稳定；
- 页面长时可使用粘性操作区；
- 失败时保留输入；
- 离开时未保存内容需要确认；
- 提交中禁用重复操作；
- 危险提交需明确影响。

---

# 第六部分：详情与信息展示

## 32. 详情页信息层级

推荐结构：

```text
PageHeader
+ 对象名称 / 状态 / 核心操作
+ 核心摘要
+ 基础信息
+ 分组详情
+ 关联数据
+ 操作记录
```

核心信息优先，不得让用户先浏览大量次要字段。

---

## 33. Descriptions 使用

适用：

- 键值信息；
- 只读详情；
- 字段关系稳定；
- 信息密度中等。

规则：

- Label 与内容对齐统一；
- 长文本支持完整展示；
- 空值有统一表达；
- 状态字段使用 Tag / Badge；
- 敏感信息按权限展示；
- 不把复杂列表塞进单个字段。

---

## 34. Tabs 与分区

Tabs 适用：

- 内容类别并列；
- 用户不需要同时对照；
- 每个 Tab 内容相对独立。

不适用：

- 信息有明显先后关系；
- 用户需要跨区比较；
- 关键内容被隐藏；
- Tab 数量过多。

Tab 数量过多时应考虑：

- 二级导航；
- 页面目录；
- 分组；
- 更多菜单。

---

## 35. Activity Timeline

适用：

- 操作历史；
- 状态变更；
- 审批记录；
- 事件过程。

应展示：

- 时间；
- 操作人；
- 动作；
- 结果；
- 备注；
- 必要的前后值。

不得只显示“已更新”。

---

# 第七部分：Dashboard 决策

## 36. 信息层级

推荐结构：

```text
全局筛选
↓
核心 KPI
↓
趋势变化
↓
维度分析
↓
明细数据
```

不得先展示大量图表而没有核心结论。

---

## 37. KPI 卡

KPI 卡应回答：

- 当前值；
- 对比值；
- 变化方向；
- 时间范围；
- 指标口径；
- 是否可点击下钻。

避免：

- 只显示大数字；
- 同时使用过多颜色；
- 变化箭头无基准；
- 指标名称模糊。

---

## 38. 图表选择

### 折线图

适合趋势和时间变化。

### 柱状图

适合分类比较。

### 堆叠图

适合总量和组成关系。

### 饼图

仅适合类别少、强调占比的场景。

### 表格

适合精确比较、明细和操作。

选择图表时先判断：

```text
用户要看趋势、比较、组成、分布还是明细
```

不得为了“丰富”页面增加无明确问题的图表。

---

## 39. Dashboard 筛选

全局筛选应影响明确范围。

需要说明：

- 影响哪些模块；
- 当前时间范围；
- 是否与局部筛选叠加；
- 数据刷新状态；
- 指标口径是否变化。

局部筛选应靠近对应模块。

---

# 第八部分：状态与异常

## 40. Loading

按等待范围选择：

- 按钮 Loading：单个操作；
- 局部 Spin：模块刷新；
- Skeleton：内容结构可预测；
- 页面 Loading：整页依赖初始化。

规则：

- 不隐藏已有可用内容；
- 避免频繁闪烁；
- Loading 时防止重复提交；
- 长时间等待提供进度或说明。

---

## 41. Empty

空状态应区分：

```text
首次无数据
筛选无结果
权限不可见
数据加载失败
功能未配置
```

每类空状态应提供不同文案和下一步。

例如：

- 首次无数据：创建；
- 筛选无结果：清除筛选；
- 未配置：前往配置；
- 无权限：申请权限或联系管理员。

---

## 42. Error

错误状态应说明：

- 发生了什么；
- 影响范围；
- 用户可以做什么；
- 是否可重试；
- 输入是否保留；
- 是否需要联系支持。

避免只显示：

```text
系统错误
操作失败
未知异常
```

---

## 43. Permission

权限不足时应根据场景选择：

- 隐藏；
- 禁用并说明；
- 显示申请入口；
- 显示只读状态；
- 阻止进入页面。

判断依据：

- 用户是否需要知道该能力存在；
- 是否可以申请；
- 是否会造成误解；
- 是否涉及敏感信息。

---

## 44. 部分成功

批量操作、导入、导出等必须支持：

```text
全部成功
部分成功
全部失败
```

部分成功应提供：

- 成功数；
- 失败数；
- 失败原因；
- 失败数据；
- 重试或下载错误数据入口。

---

# 第九部分：响应式与溢出

## 45. 响应式原则

响应式不是简单缩放，而是调整：

- 布局；
- 优先级；
- 展示方式；
- 操作位置；
- 内容密度；
- 交互容器。

优先级：

```text
保留核心任务
→ 保留主操作
→ 保留关键数据
→ 折叠次要操作
→ 降低列数
→ 切换容器
```

---

## 46. 窄屏处理

### 页面头部

- 标题和操作允许换行；
- 主操作优先；
- 次要操作进入更多；
- 状态与标题不重叠。

### FilterBar

- 列数逐级下降；
- 操作区保持可见；
- 展开收起可用；
- 不产生字段截断。

### TableToolbar

- 允许换行；
- 批量操作和已选摘要优先；
- 工具类操作可折叠。

### 左右布局

- 左侧可折叠为 Drawer；
- 或转换为顶部选择；
- 不得让主内容宽度不可用。

---

## 47. 表格溢出

原则：

- 页面自身不出现无意义横向滚动；
- 宽表格只在表格容器内滚动；
- 关键列固定；
- 操作列可固定；
- 固定列阴影明确；
- 移动端可考虑卡片化，但需保持信息完整；
- 不通过缩小字号解决所有列。

---

## 48. 长文本

处理方式：

- 截断 + Tooltip；
- 展开收起；
- 独立详情；
- 多行显示；
- 固定最大高度。

选择依据：

- 内容重要性；
- 用户是否需要比较；
- 是否高频查看；
- 页面密度；
- 可访问性。

不得对关键信息仅用 Tooltip 隐藏。

---

# 第十部分：一致性与复用

## 49. 现有模式优先

设计前必须检查：

- 是否已有同类页面；
- 是否已有业务组件；
- 是否已有相同容器；
- 是否已有工具栏；
- 是否已有状态样式；
- 是否已有 React / Vue 对照实现。

如果已有模式满足需求，应优先复用。

---

## 50. 一致性不是机械复制

允许因场景不同调整：

- 字段数量；
- 操作优先级；
- 内容密度；
- 容器大小；
- 响应式策略。

但以下内容应保持一致：

- 同类操作位置；
- 主次操作语义；
- 状态表达；
- Token；
- 组件行为；
- 危险操作；
- 查询与重置；
- Popup 和 Portal；
- React / Vue 结果。

---

# 第十一部分：信息不完整时的处理

## 51. 可合理推断

当以下信息明确时，可以基于现有模式推断：

- 任务类型；
- 框架；
- 最近似模板；
- 已有组件；
- 明确业务目标。

推断时应说明依据。

---

## 52. 必须确认

以下情况应标记待确认：

- Figma 与 Token 冲突；
- 公共 API 需要变化；
- 业务行为不明确；
- 危险操作影响范围不明；
- 数据量和性能要求不明；
- 是否需要双端不明确且影响交付；
- 容器选择会影响路由和状态恢复；
- 页面模板可能演变为公共框架；
- 权限和敏感数据规则不明。

不得自行猜测关键业务规则。

---

## 53. 临时降级

受环境或信息限制时，可以：

- 先提供结构方案；
- 使用本地 Mock；
- 标记未验证；
- 保留待确认项；
- 使用已有最接近模式；
- 停止在只读分析或实施计划。

不得把临时方案描述为最终标准。

---

# 第十二部分：设计审查清单

## 54. 布局

- 是否有明确主内容；
- 页面结构是否符合任务顺序；
- 左右或上下结构是否有依据；
- 信息层级是否清晰；
- 是否存在过度卡片化；
- 间距是否使用 Token；
- 窄屏是否可用。

## 55. 容器

- Modal / Drawer / 新页面选择是否合理；
- 内容体量是否匹配；
- 是否需要上下文对照；
- 是否需要独立 URL；
- 是否支持保存和恢复；
- 是否存在嵌套容器风险。

## 56. 操作

- 主操作是否唯一；
- 次操作是否降级；
- 危险操作是否明确；
- 批量操作是否靠近选择反馈；
- 行操作是否过多；
- 操作反馈是否完整；
- Loading 时是否防重复。

## 57. 筛选与表格

- 常用筛选是否优先；
- 高级筛选是否合理收纳；
- 查询和重置语义是否清晰；
- TableToolbar 是否职责清楚；
- 列设置是否必要；
- 导出范围是否明确；
- 分页和跨页选择是否完整；
- 宽表格是否局部滚动。

## 58. 表单

- 字段是否合理分组；
- 单列和多列是否合理；
- 是否需要分步；
- 错误是否就近；
- 离开是否保护未保存内容；
- 提交失败是否保留输入；
- 操作区是否稳定。

## 59. 详情与 Dashboard

- 核心信息是否优先；
- 详情分组是否清晰；
- Tabs 是否必要；
- KPI 是否有口径和对比；
- 图表是否回答明确问题；
- 全局筛选影响范围是否清楚。

## 60. 状态与异常

- Loading；
- Empty；
- Error；
- Permission；
- Partial Success；
- Disabled；
- Offline / Timeout；
- Recovery。

## 61. 一致性

- 是否复用已有组件；
- 是否使用正确 Token；
- 是否符合 React / Vue 一致性；
- 是否符合已有页面模式；
- 是否避免重复实现；
- 是否有 Docs 和验证依据。

---

## 62. 常见错误

### 62.1 只根据截图做决定

问题：

- 忽略行为；
- 忽略状态；
- 忽略响应式；
- 忽略组件能力；
- 容易产生局部硬编码。

### 62.2 所有内容都放 Modal

问题：

- 内容过多；
- 滚动复杂；
- 无法恢复；
- 无独立 URL；
- 嵌套严重。

### 62.3 所有页面都做卡片

问题：

- 层级混乱；
- 空间浪费；
- 视觉噪音；
- 无法突出主内容。

### 62.4 所有操作都直接展示

问题：

- 工具栏拥挤；
- 主次不清；
- 窄屏不可用；
- 用户认知成本高。

### 62.5 为减少页面高度盲目多列

问题：

- 阅读顺序混乱；
- 错误提示拥挤；
- 长字段不可用；
- 响应式困难。

### 62.6 只设计正常态

问题：

- Loading、Empty、Error 缺失；
- 失败后无法恢复；
- 权限不清；
- 真实业务不可用。

### 62.7 复制页面而不抽取稳定能力

问题：

- 重复代码；
- 视觉分叉；
- React / Vue 难以维护；
- Skill 无法复用。

### 62.8 过早封装万能组件

问题：

- Props 爆炸；
- 互斥组合；
- 页面逻辑污染组件；
- 难以测试和发布。

---

## 63. 快速决策示例

### 示例一：表格行编辑

```text
目标：编辑当前行
关联性：强
内容体量：中等
需要上下文：是
独立 URL：否
推荐：Drawer
不推荐：新页面或小 Modal
```

### 示例二：复杂活动配置

```text
目标：完成多步骤配置
内容体量：大
流程：复杂
需要草稿：是
需要恢复：是
推荐：新页面 + Steps
不推荐：Drawer
```

### 示例三：删除确认

```text
目标：确认高风险操作
内容体量：少
关联性：强
推荐：Popconfirm 或 Modal
需要明确影响范围和不可恢复性
```

### 示例四：标签管理

```text
目标：频繁切换标签并管理列表
左侧：稳定标签组
右侧：筛选、工具栏、表格
推荐：左右结构
窄屏：左侧转 Drawer 或顶部选择
```

### 示例五：表格批量停用

```text
触发：选择数据后
位置：表格左上方
反馈：已选择 N 项
风险：高
确认：说明影响数量和范围
结果：成功/失败明细
```

### 示例六：Dashboard 指标页

```text
顺序：
全局筛选
→ KPI
→ 趋势
→ 维度分析
→ 明细表格

图表必须回答明确问题
```

## 64. 完成标准

一个设计决策只有满足以下条件时，才能判定为可执行：

1. 明确用户目标；
2. 明确核心任务；
3. 明确内容体量；
4. 明确上下文关联；
5. 明确操作频率和风险；
6. 选择了合理布局或容器；
7. 说明了不推荐方案；
8. 明确复用组件；
9. 考虑主要状态；
10. 考虑响应式和溢出；
11. 未违反架构边界；
12. 可由 React / Vue 和现有组件实现；
13. 待确认项已明确；
14. 决策依据可解释、可复用。
